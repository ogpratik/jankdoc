# Pure-Dart in-memory vector store for v1; interface-first for future swap

The RAG corpus starts at ~50 patterns. At that scale, brute-force cosine similarity over in-memory float vectors runs in under 0.1ms — LanceDB's sub-50ms p99 claim is irrelevant, and LanceDB-via-FFI introduces a Rust toolchain dependency that complicates distribution (pub packages don't ship Rust binaries). sqlite-vss has the same FFI distribution problem.

Decision: ship a pure-Dart `VectorStore` interface with an `InMemoryVectorStore` implementation that persists to a JSON file on disk. Embeddings are generated by Ollama (`nomic-embed-text`) via HTTP — no native dependency. The interface is swappable; when the community KB grows past 10k patterns, drop in a LanceDB or sqlite-vec implementation without touching the analysis daemon's business logic.

## Considered options

- **LanceDB-via-FFI** — correct at scale, wrong at v1. Adds Rust toolchain, no Dart SDK exists (requires writing FFI bindings), and provides zero latency benefit over 50 patterns.
- **sqlite-vss / sqlite-vec** — better than LanceDB for Dart (sqlite3 package exists), but still requires loading a native extension at runtime, which is a distribution and sandboxing risk inside DevTools.
- **Pure-Dart + JSON persistence** — zero dependencies, ships in the daemon binary, trivially testable, upgradeable later.
